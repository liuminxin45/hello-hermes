# 写作修订与审稿意见处理

担任技术图书编辑、Agent 系统架构审稿人和教学设计审稿人。审查现有内容并修复真实问题，不重新生成全书，也不以改字数或扩写篇幅衡量质量。

本书面向会使用聊天 AI、没有 Agent 架构基础的中文读者。学习终点是解释模块责任、数据与控制流、状态变化和设计取舍，并能迁移分析新需求。读者无需安装 Hermes、理解 API、编程或阅读 Python；易懂不能以牺牲必要的工程深度为代价。

## 用途、场景与阶段选择

本 Skill 由写作模型承担，区分两个入口，不把作者自检当作独立盲审：

| 入口 | 适用请求 | 输入与交付 |
| --- | --- | --- |
| 阶段 A：写作与修订 | 批量优化当前内容、全书审稿并修订、系统性编辑审计 | 依据课程与当前成稿通读、登记、最小修订、自检，执行构建与检查，保存编辑报告。 |
| 阶段 C：处理审稿意见 | 逐条核实盲审意见、根据指定审稿报告修订 | 以用户提供或指定的报告为输入，先验证意见，再只修复成立部分，保存逐项处理结果。 |

阶段 C 先读 [references/review-response.md](references/review-response.md)，按该流程定位和验证，不重新从阶段 A 发起全书批量优化。已给出待处理报告时优先走阶段 C；仅有一句“处理审稿意见”而没有报告时，获取缺失的报告或位置，不编造意见或擅自读取历史会话。

“盲审”“独立审稿”“全书只审不改”属于阶段 B，使用 `../hello-hermes-blind-review/SKILL.md`，不进入本 Skill 的修订步骤。如果用户要求只验证已有报告、不改稿，则仍是阶段 C 的只读核实，不改走禁止读取报告的盲审流程。普通局部润色按指定范围处理，不自动扩大到全书；新章写作仅在明确授权后按课程大纲推进。

仅请求某一阶段时完成后结束，不自动切换模型或进入下一阶段。明确授权 A → B → C 全流程时可按依赖串行执行：A 完成后，B 由不同于写作模型的实际模型在全新上下文盲审，C 再由写作模型核实意见。传给 B 的资料只含成稿、项目约定、原始技术来源与必要的版本、模型身份等中性信息，不含 A 的问题清单、修改理由或自检结论。更换角色、重新开上下文或在提示词里写“另一模型”均不能证明实际模型不同；无法确认时如实说明，不宣称 B 已完成。Skill 不固定具体模型名称或推理档位。

## 调用范围与执行边界

- 在选定的 A 或 C 范围内完成核实、最小必要修订、自检与验证，不逐章请求确认。用户只要求核实已有意见时在 C 中保持只读，仅输出判断；用户只要求审当前原稿时按 B 路由。两种只读任务均不自动写报告文件，不修改正文、配图或核对记录；缩小范围时尊重指定范围，不声称完成全书审计。
- 用户只要求保存、整理或修改本 skill 时，仅维护 skill 及必要入口，不执行其描述的审稿任务。
- 在当前工作目录工作，不创建额外 worktree、不复制整个仓库。先检查 Git 状态与已有差异，保留用户修改，不 reset、clean 或覆盖无关文件。必要时记录待改段落的原文，供前后对照和撤回本轮修改。
- 本流程不修改软件功能，不自动提交、推送、创建 PR 或发布，也不因审稿自动升级 Hermes 核对版本。用户另行授权的后续工作按该任务执行。
- “跟上官方最新”使用项目的 `hello-hermes-sync` skill；处理本地批注按 `editorial/review-workflow.md` 执行 `list`、`begin`、验证与核销。审计本身不消费或核销批注，不直接写 `.review/annotations.json`。

## 先理解当前课程

按项目根目录解析下列路径，先读：

阶段 A 完整阅读下列范围；阶段 C 先读 1–3，再围绕报告涉及的章节、课程目标、案例和受影响依赖核实，不把局部意见处理扩大为全书审计。

1. `AGENTS.md`。
2. `editorial/writing.md`、`editorial/curriculum-design.md`、`editorial/visuals.md`。
3. `content/chapters.json`、`content/verification.json`、`editorial/figures.json`。
4. `docs/preface.md`、`docs/roadmap.md`、`docs/casebook.md`。
5. 当前目录中所有 `status: published` 单元的正文：由 `path` 解析为 `docs/<path>.md`；按目录顺序阅读，并检查 `prerequisites`、`outcome` 与 `artifact`。需要时读其引用的固定案例材料、观察记录和内部审核记录。

章节数、编号、专题和路径以当前目录为准，不固化“18 章”或猜测文件名。新版位于 `docs/learn/`；`docs/chapters/`、`content/archive/` 作为旧版保留，不属于本轮修改范围，不继承旧版核对完成态。规划单元只检查其目录中的依赖关系，不创建空正文或加入阅读导航、搜索。

以现有课程设计、两张统一主图、贯穿案例和版本规范为基础；提出结构变动必须说明实际缺陷，不无理由推倒已有设计。

## 阶段 A：通读、登记，暂不修订

完整阅读上述范围，再开始改稿。按三个视角逐章审查；详细检查点见 [references/review-criteria.md](references/review-criteria.md)，本阶段必须阅读。

- **逻辑审稿人**：追问结论的前提和完成标准，分清模型判断、程序控制、工具执行与结果验证，识别因果错误、概念矛盾和绝对化能力描述。
- **初学者**：追问为什么关心本章问题、术语是否已有铺垫、例子怎样通向机制、每节建立了什么认识；避免抽象概念拥挤和幼稚化语言。
- **架构设计者**：追问模块如何工作，输入、输出、状态、交互与责任是否清楚，Hermes 的选择、替代方案及代价是否足以支持迁移分析。

在 `editorial/reviews/` 建立本轮报告，文件名使用实际审计日期 `YYYY-MM-DD-editorial-audit.md`；同日重复执行使用序号后缀，不覆盖历史报告。先写初始问题清单，后续在同一报告补充修订与验证结果。

每个问题记录稳定编号、优先级、文件和小节（必要时行号）、足以判断的原文、缺失前提或具体影响、依据、建议及依赖章节。事实待核实时标明“待核实”，不要把怀疑写成已确认缺陷。每章都记录已读状态与具体判断，包括质量足够、无需修改的章节；未读不得算作无问题。

## 阶段 A：跨章审计与排序

检查知识依赖、两张主图的术语和职责、贯穿案例的累积、各章机制深度、同一概念的定义和边界，以及综合项目能否检验已有知识。复核理解题是否能由当前及前置章节推出答案。

检查反复铺垫、机械预告和限制声明是否损害阅读节奏。某种表达反复出现不自动构成问题；只有影响理解、节奏或体验才登记修改。

本 skill 使用以下编辑优先级：

| 优先级 | 判断依据 |
| --- | --- |
| P0 | 技术事实错误、因果逻辑错误、前后矛盾 |
| P1 | 严重教学或架构缺陷：关键前置、机制、状态或交互缺失，阻断承诺的学习成果 |
| P2 | 阅读体验问题：术语、衔接、图文或表达造成具体理解阻力，不以个人文风偏好立项 |

与阶段 B、C 统一使用 P0/P1/P2。先形成按严重程度排序的问题清单，再按章节依赖关系组织修订：先 P0、P1，再 P2。没有明确缺陷的细节不立项，不按文件顺序机械替换。

## 阶段 A、C：最小必要修订

1. 正确、自然、清楚的原文直接保留。修复原因：逻辑不完整就补前提，架构不清楚就补机制，过渡突兀就补段落间的因果关系。
2. 使用自然、平实、准确、有层次的中文。避免连续设问、机械排比、空泛总结、口号化结论和概念堆砌；不把去除模板感变成删除关键设计推理。
3. 保留必要的数据流、控制流、状态变化、替代方案与失败边界。核心机制不能仅靠章末总结、概念列表或“实际还很复杂”带过；充分的内容不再扩写。
4. 严谨但不过度防御。教学示意、源码确认、受控模块实验和完整模型运行要分清，把范围说明放在合适位置，不在每段重复免责声明。不把记忆或技能更新写成模型权重训练。
5. 更改案例、名词、状态、权限或结论时，检查其前置与后续依赖，同步必要引用和图文，避免新旧设定并存；不顺手重写无关章节。
6. 具体技术事实查 `content/verification.json` 中该章的固定版本，核实相关官方源码与测试，并参考对应官方文档。不能凭通用 Agent 常识猜测 Hermes 实现；证据无法取得时保留缺口，改为有依据的限定表述或暂缓该项，不编造机制。
7. 正文维持内部证据展示规范，不新增读者可见的源码跳转、引用横幅或编辑入口。必要依据进入本轮内部报告；确需更新核对记录时只更新实际核实的范围，保留原依据，不能以文字润色、报告生成、构建或部署刷新 `verifiedAt`、版本和完成态。
8. 改图前按 `editorial/visuals.md` 先写图意，使用规定的制图流程，核对箭头、标签、分支、边界、alt、图注及正文，并按实际情况维护图解记录。工具不可用时保留待补状态，不以旧图或占位图冒充验收完成。

## 阶段 A、C：修订后自检

回读每个实际修改过的章节及其受影响上下文，结合原文、问题清单与最终差异逐项判断。这是写作模型对自身修订的自检，不是阶段 B 的独立盲审，不把完成修改等同于通过检查。

- 原问题是否真正解决，有什么具体证据？
- 是否引入新前提、逻辑漏洞或跨章矛盾？
- 是否损失有价值的技术细节，或把具体事实改为空泛表达？
- 普通读者是否更容易理解，机制和设计取舍是否仍然清楚？
- 能否明确说明相较原文的收益？

无法说明收益的本轮修改应撤回，只撤回自己的改动，保留用户原有修改。记录自检结果和仍未解决的事项，不给自己打笼统高分。

## 验证与报告

需要改稿时记录可取得的现有测试与构建状态，必要时执行基线检查，用于区分原有失败与本轮引入的问题；无法取得基线时，失败归因标为未确认。修订完成后：

- 检查 Markdown、交叉引用、术语、案例状态和图文一致性，执行 `git diff --check`。
- 执行 `npm test`、`npm run docs:build`。构建包含 `scripts/check-public-output.mjs`，必须确认公共产物无批注控件、接口脚本、数据或凭据；不得提交 `.review/`、草稿和会话凭据。
- 涉及远程链接时执行 `npm run check:links`；网络不可达与链接已失效分别记录，不能将未验证写成通过。
- 对改动的阅读页作必要浏览器检查：桌面与手机、深浅主题，检查正文、表格、图解可读性及放大交互。按变化检查导航、搜索和相邻页衔接。没有页面变化时说明视觉检查不适用。
- 测试、构建、浏览器、源码核对和实验分别记录命令或页面范围、实际结果与限制。工具不可用或检查失败时如实写未完成，不伪称通过，也不为通过检查修改软件功能或掩盖既有失败。

阶段 C 仅修复确认成立的部分。若逐项核实后没有内容变化，交付判断和依据，不为产生差异而改稿；无新增变化或未解决疑虑时不重复运行构建、测试与视觉检查，不因处理报告完成宣称所有意见已修复。

阶段 A 的编辑报告至少包含（阶段 C 使用 `references/review-response.md` 的逐项处理格式）：

1. 审计范围、实际阅读覆盖、工作区基线、使用的固定版本与证据性质。
2. 按优先级排序的问题、具体位置、原文及判断依据；保留初始发现和最终处理状态。
3. 每项重要修改的原因、前后对照、关联章节与自检结论；暂缓或不修改的理由。
4. 已修改章节和因质量足够而保持不变的章节，区分未审章节。
5. 未解决的架构深度、教学设计、证据与待补图缺口，以及后续优先级。
6. 测试、构建、链接、浏览器与公共输出检查的实际结果，区分原有失败、本轮问题和无法归因项。

阶段 A 汇总报告路径、原书最严重的三个问题（不足三个时按实际数量）、实际修复、暂时不应修改的事项及理由、剩余风险与后续优先级；阶段 C 按意见编号汇总核实和处理结果。两者均说明这是写作方自检，是否完成阶段 B 另据实际执行情况说明。验收依据是内容更严谨、教学更顺畅、架构理解更深入，且原有正确内容得到保留。
