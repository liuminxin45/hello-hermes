# 三个审稿视角与跨章检查

在完整阅读、登记缺陷时使用。检查点用于追问具体问题，不要求每章复制相同结构、补齐相同篇幅，或为了满足条目而修改充分的内容。

## A：逻辑是否成立

- 结论是否由已交代的前提推出，有没有偷偷增加用户未提出的任务要求？
- 完成标准是否先于成败判断出现，是否区分任务完成、工具成功、请求成功和结果验证？
- 是否把理想行为或一次成功观察写成真实 Agent 必然具有的能力？
- 模型判断、程序控制、工具执行是否分清，行为和状态由谁落实？
- 是否存在概念不一致、因果倒置、绝对化判断，或经不起追问的解释？
- “应该”“可能”“实际实现”“本次观察”是否与依据相符？

例如：“你让 AI 根据三份材料整理三条消息。它生成了三段话，但没有解决任务。”

如果此前没有明确去重、真实性和完成标准，不能仅由“三段话”推出“任务未完成”。应先核实真实任务要求及材料，再补齐前提与判断标准的关系；不能为了让批评成立而擅自增加要求，也不能只把结论改得更委婉。

## B：初学者能否建立认识

- 本章主问题是否容易理解，读者为什么会关心？是否先有可理解的困难，再引入机制？
- 术语是否在需要时解释，是否依赖读者尚未学到的知识？不能默认读者懂 Tool Registry、Session、Provider、Runtime 或 Context Compression。
- 是否连续引入过多抽象概念；能否借输入输出、状态对照和例子建立直觉？
- 是否出现读者尚不知道的问题，却直接给出技术答案？
- 故事、例子与架构解释是否自然衔接，每节带来什么明确的新认识？
- 图表是否回答具体问题，正文是否补足条件和推理，而非把同一段话重复画写？
- 是否有重复铺垫、机械预告或过度解释；删改是否确实改善阅读节奏？
- 语言是否尊重读者的判断能力，避免幼稚化比喻与说教？
- 理解题是否可以由本章和前置章节推出，答案有没有依赖后章、源码或未交代的前提？

## C：是否理解了架构

- 该模块解决什么问题，缺少它的简单方案会在哪里失效？
- 是否从“是什么”推进到“如何工作”，讲完整一条主流程？
- 输入、输出、状态及状态归属是否清楚，哪些条件触发状态转换？
- 关键模块间的数据怎样流转、控制权怎样交接，判断与执行分别由谁承担？
- 是否充分说明固定版本 Hermes 的实际设计，而非只复述通用 Agent 概念？
- 教学分层、系统责任图和实际部署是否区分，是否把理解视图误写成官方源码的严格分层？
- 是否遗漏影响理解的关键设计思想；该思想应在正文哪里解释？
- 是否比较至少一种相关且合理的替代方案，讲清收益、代价、限制及适用条件？
- 是否有足够的机制、状态变化或推演材料，让读者迁移到另一个 Agent 系统或新需求？
- 是否只有概念列表、章末总结或“还需处理复杂情况”，缺少必要的设计推理？
- 已经充分的内容是否应保持原样，避免为表现深度增加无效篇幅？

## 跨章整体审计

1. 对照 `prerequisites` 与正文实际用到的知识，检查提前引入、循环依赖和深度断层。
2. 对照系统责任图、任务时序图及其局部图，检查术语、模块边界、箭头和状态定义。
3. 沿贯穿案例追踪每章输入与产物，检查它是否逐步累积，而非换个说法重复同一故事；权限、完成标准、材料和任务状态是否一致。
4. 比较同一概念在不同章节的定义、因果解释和失败边界，检查基础章是否提前承担过多工程细节。
5. 检查“本章产物”“下一章会讨论”“这不代表”等表达，只有实际损害节奏或理解时才修订，不按词频机械清除。
6. 检查严谨性说明的位置和重复程度，保留必要边界而不过度防御。
7. 检查最终综合项目是否要求运用已讲原理、选择必要模块、解释可以省略的能力，而非仅复述模块名称或依赖未教知识。

## 证据边界

固定版本源码与测试、官方文档、受控模块实验、真实模型运行和教学推演各有证明范围。对照内部记录核实，不虚构运行轨迹、实验、验证结果或核对日期；尚未采集的真实运行证据不自动构成所有机制必须重写的理由。明确指出缺口会影响哪个结论，以及当前能作出的有限判断。
