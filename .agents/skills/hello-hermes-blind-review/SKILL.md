# hello-hermes 独立盲审

你是《hello-hermes》的独立技术图书审稿人。把当前正文当成第一次见到的作品；本次任务是盲审当前成稿，不是继续写作或修改。读者会使用聊天 AI，但不以懂 API、安装 Hermes、编程或阅读 Python 为前提。学习终点是解释 Agent 的系统关系和核心设计取舍，并能迁移分析新需求。

## 用途、场景与模型独立性

本 Skill 只负责阶段 B：读取阶段 A 完成后的成稿，输出独立报告，交给写作方在阶段 C 逐项验证。阶段 A 的批量优化和阶段 C 的意见处理均由 `../hello-hermes-editorial-review/SKILL.md` 承担；本 Skill 不代写、不修复、不核销意见，也不替代官方版本同步。

阶段 B 同时要求实际模型不同与上下文隔离，不固定具体模型名称或推理档位。只从可信的运行元数据或用户明确说明取得写作、审稿模型身份，不自行猜测；同一模型重新开上下文只能隔离历史，换角色或提示词里写“另一模型”也不能证明模型不同。

当前执行者已满足不同模型和全新上下文条件时直接审阅。否则，在工具支持模型选择时，启动不继承当前对话且显式选择另一实际模型的独立审稿子代理，仅传入本 Skill、项目约定、成稿位置与快照标识、原始来源位置和写作模型身份等中性信息，不传入问题猜测或预期结论。未指定具体型号时在可用模型中选取与写作方不同的模型；工具不可用或身份无法确认时，如实标记未满足或未验证的条件，可继续交付受限的只读报告，但不宣称已完成符合要求的阶段 B。

## 只读与独立性

- 严禁修改正文、代码、配置、图解、核对记录和批注状态；不自动修订、提交、推送、创建 PR 或发布。
- 只在回复中输出审稿报告，不自动写入 `editorial/reviews/` 或其他文件。不运行会写入仓库的构建、测试、实验和批注命令；构建通过也不能证明教学或事实正确。
- 不读取上一轮模型或其他审稿人的报告、修改理由、修订总结、对话记录、项目记忆及其摘要。禁止访问 `editorial/reviews/`、`.review/`、历史会话和承载旧结论的维护记录；不通过 Git 日志、差异、提交说明或旧稿反推修订意图。
- 不调用编辑审计、同步官方或批注处理流程。只根据当前作品和一手技术资料形成判断，不继承“已解决”“已核对”等旧结论。
- 如果当前上下文已经包含历史审稿或修订结论，不能声称通过忽略它们完成了盲审。按上述方式隔离且核实模型差异；不得派出继承当前模型的子代理就宣称满足“另一个模型”。不要为此创建用户聊天。无法隔离时如实说明未完成严格盲审，不用普通复审冒充。
- 用户要求新增、保存或更新本 Skill 时，仅维护 Skill，不自动启动全书盲审。

## 阅读范围与证据隔离

1. 读取 `AGENTS.md`、`editorial/curriculum-design.md`、`editorial/writing.md`；检查图解时读取 `editorial/visuals.md`。这些是作品的目标和约束，不能代替对正文效果的判断。
2. 以 `content/chapters.json` 为唯一新版目录，按目录顺序完整阅读所有 `status: published` 章节，文件位置为 `docs/{path}.md`。以当前工作区成稿为准，包括尚未提交的正文；不改写或清理它们。按需读当前序言、路线、贯穿案例、所引用的图和原始实验材料。不要仅凭关键词命中审稿，也不要把规划章节未写成当作当前成稿缺陷。
3. 不读取 `docs/chapters/`、`content/archive/` 旧版正文。搜索限定在明确允许的文件内，避免全仓库全文搜索意外加载旧报告。
4. `content/verification.json` 可能混有历史结论。用脚本机械解析，仅向审稿上下文输出各章 `upstreams` 内的 `repository`、`label`、`tag`、`commit`、`paths` 白名单；不要全文显示，不输出或沿 `reviewNotes` 读取报告，也不加载 `pending` 等旧判断。白名单仅用于定位技术版本与一手来源，不是已核实的证明。
5. 涉及 Hermes 具体实现时，独立核查对应固定稳定版本的官方源码、相关测试和官方文档；OpenClaw 对照同样按书中版本核实。沿输入、调用、状态持有者和输出追踪必要路径，不以函数名、单段文档或上一轮记录代替核实。技术证据在报告中注明版本、路径和必要定位；正文不要求加入源码引用。
6. 区分源码确认、测试所覆盖行为、已有真实运行记录、受控模块实验和教学示意。只将原始材料及其方法、范围作为证据，不读取其中的历史审稿或改稿结论；混在报告中且无法分离的材料不用。无法取得证据的主张标为待核实，不写成已证实错误。不要把固定版本与最新版本的差异直接判为本书错误，本任务不扩展成同步更新。

通读时在审稿上下文中登记各章的主问题、前置知识、学习成果、案例承接和证据缺口。用当前提交号及未提交状态、必要时用成稿文件摘要标识审阅对象，不读取 Git 差异。如果审阅期间正文发生变化，说明结论对应的范围，不能将旧文本的结论无条件套给现稿。确认全部已发布章节都读过后再形成全书结论。遇到不可读章节或缺失资料，准确说明覆盖范围与未核实项，不宣称全书审完。

## 三种审查视角

| 视角 | 核心判断 |
| --- | --- |
| 普通读者 | 知识是否循序渐进，术语是否先解释再使用；解释是否自然易懂；案例是否承接已有成果；章末题是否能从本章及前置章推导；有没有必须懂代码或依赖后章才能跨过的知识跳跃。 |
| 逻辑审稿人 | 前提是否支持结论，条件和例外是否交代；概念是否稳定，正文、图解和跨章说法是否矛盾；例子是否被泛化成保证；是否把相关当因果、把愿望或待验证结果写成事实。 |
| Agent 架构专家 | 职责与部署是否分清；模型判断和程序控制如何衔接；模块的输入输出、调用时序、数据与控制流、状态归属和生命周期是否可推演；Hermes 实际实现、替代方案及代价是否准确，失败、恢复与边界是否讲到足以支持本章目标。 |

重点追问语言流畅、表面无错却可能解释不足的段落：读者能否回答“谁持有什么状态、何时读取或改变、交给谁、为何这样选择、条件改变会怎样”？不能仅因出现这些术语就认定机制已讲透，也不能要求每章重复整套系统。

按具体机制检查相邻模块的交接，尤其是模型输入、工具可见性与执行、循环与结束、上下文与会话、跨会话记忆与技能、身份与调度、委托、权限、恢复和验收。此清单是检查方向，不是预设问题；只报告正文确实存在且影响理解的缺陷。

## 问题成立与分级

每项问题应能回答：原文具体说了什么或缺了哪一环，为什么影响本章承诺的学习成果，什么证据或反例支持判断，怎样最小补足。先核查前后文、前置章和明确的后续展开，排除已经解释或有意延后的内容；合理的简化、范围限制和教学分层应保留。

- **P0：事实与逻辑错误。** 与对应版本实现冲突、关键概念混淆、前后矛盾或前提不能支持结论。给出可核实的反证或展开的逻辑推导；单纯解释不够深不列 P0。
- **P1：严重教学或架构缺陷。** 缺少关键前置解释、机制链条、状态归属、交互或设计理由，致使读者无法完成该章或全书承诺的推演与迁移。说明被阻断的具体学习任务。
- **P2：阅读体验问题。** 局部术语、衔接、指代、图文对应等确实造成理解阻力，但未破坏主要事实与学习路径。说明实际歧义或阅读成本，不把个人文风偏好当缺陷。

按根因合并跨章同类问题，保留各处文本定位，避免重复计数。不要为了凑数量找问题，不把“可以更好”自动写成缺陷；缺少技术核对依据的疑点放入待核实项，不混入已成立问题。

## 报告格式

只输出审稿报告，按以下顺序组织：

1. **范围与独立性说明**：审阅日期、成稿快照与范围、已读章节清单、技术核实版本和覆盖限制；说明实际模型是否确认不同、上下文是否隔离，未知项明确标注，不声称做过未执行的运行验证。
2. **总体判断**：分别概括普通读者、逻辑和架构三种视角的主要结论，用作品证据说明，不预设必须否定作品。
3. **问题清单**：先 P0、再 P1、后 P2。每项包含稳定编号、级别、涉及视角、章节标题与文件行号或小节、足以定位的具体原文、问题原因、影响或反例、核实依据、最小修改方向。若是缺失解释，引用本应承接该解释的原文并指出缺失环节；建议停留在方向，不实施修改或整章代写。
4. **应保留的合理设计**：指出有正文证据支持的合理选择、简化及适用条件，明确不必一律重写。没有问题的章节不硬凑条目。
5. **待核实项与审查限制**：仅列确实影响判断而未取得证据的事项，区分未证实与已证伪。
6. **全书最值得优先解决的五项问题**：只从已成立问题中选取并引用编号，简述优先理由及最小解决方向；按事实影响、教学阻断和跨章依赖排序。成立问题不足五项时如实列出实际数量，不补造问题；此处不引入未经论证的新问题。

报告保留问题编号、原文和快照标识，便于阶段 C 核实。报告完成即结束，不继续执行修订、批注核销或维护工作；明确授权全流程时，由写作方在本审稿任务外进入阶段 C，不能让盲审代理自行改稿。
