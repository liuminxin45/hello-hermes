# 第九章：经验怎样成为可复用的方法

简报连续做了几次，你发现每次都要重新提醒：“先去重，再回到原公告核对，资料不足时不要凑数。”这是一套做法，可以保留下次复用。

如果只保存最终两条草稿，下一次换一组材料就未必有用。如果把做法写成带前提和验证方式的方法，新的任务便有了可以参考的起点。这是技能系统所要组织的经验材料。

本章的产物是一份简报技能草案。你需要解释它什么时候适用、怎样被发现和使用、什么结果能说明它仍然有效，以及什么时候应该修订。

## 9.1 事实、答案与方法

用户喜欢短简报，是偏好；A 支持纯文本导出，是特定材料中的事实；这次的两条草稿，是交付；怎样处理重复和冲突，才是可迁移的方法。

| 保存对象 | 下次能直接复用什么 | 主要风险 |
| --- | --- | --- |
| 最终答案 | 部分表达方式 | 旧事件与旧条件被当作新事实 |
| 原始操作记录 | 做过什么、怎样失败 | 细节太多，难以识别真正有效的方法 |
| 经整理的技能 | 适用条件、步骤与判断 | 过度概括或固化错误经验 |

提炼技能需要从经历中区分因果和偶然。“这次试了三次才成功”不应直接写成“所有失败都重试三次”。真正可复用的是先判断错误原因与动作影响，再选择合适的有限尝试。

## 9.2 为什么不把全部技能都放进每轮输入

技能库可能包含研究、写作、设备操作等大量方法。每次全部读入，会占据上下文，混入无关步骤，还可能让彼此适用条件不同的说明同时影响任务。

Hermes 用渐进披露来组织技能：先通过名称、描述和相关条件发现候选，再按需要读取详细方法与资源。可以把它理解为先看目录，确认相关以后再打开正文。

这种设计减少常驻材料，也把一项责任交给发现与选择过程。如果描述叫“万能助手”，很难判断何时使用；“核对固定材料、去重并标注未知的消息简报”则给出了明确场景。

目录信息、被选择的说明和真正执行的动作是不同状态。技能已经存在于库中，不表示本次一定加载；加载了也不表示步骤已经执行成功。

## 9.3 一份技能怎样进入任务

沿简报主线可以分成以下环节：

1. 当前目标触发相关技能的发现。
2. 读取详细方法，核对适用条件和所需能力。
3. 将方法与本次材料、用户要求结合。
4. 通过工具取得真实结果，再按标准检查。
5. 有必要时修订方法，而不是把失败隐藏在一份成功摘要中。

技能文档通常以 SKILL.md 为入口，还可以包含参考资料、模板或辅助脚本。它不必是一个程序，却可以指导程序与模型怎样配合。是否有配套脚本，取决于任务需要。

比如固定格式检查适合由确定性程序处理；A 与 B 的说法是否冲突，需要依据材料解释。把两者分开，可以减少机械工作，也让重要判断更容易观察。

## 9.4 为消息简报写一份方法草案

下面是教学草案，重点是方法结构，不是完整的安装格式：

| 项目 | 简报方法中的内容 |
| --- | --- |
| 适用场景 | 整理一组有原始来源、可能包含转述的消息 |
| 必要输入 | 时间范围、材料范围、篇幅偏好、是否允许投递 |
| 关键判断 | 同一事件去重；冲突回原文；限制与未知保留 |
| 行动方式 | 按需读取，不把工具成功等同核实完成 |
| 交付标准 | 事件不重复、结论不超范围、资料不足时解释 |
| 失效信号 | 原文不可得、规则变更、连续出现同类遗漏 |

方法没有规定永远输出两条，也没有把公告 A 的某项结论写成通用事实。这样下一周换材料时，仍然能复用判断方式。

如果方法需要的读取能力不可用，应说明缺口或选择允许的替代路径。技能可以告诉模型怎么做，却不能凭文档让一个不存在的工具突然具有访问能力。

## 9.5 为什么这不同于训练模型

技能被创建或修改后，改变的是系统以后能够发现和带入的材料。模型读到更合适的指导，可能少走弯路；这不表示它的内部权重已经因这次任务完成了训练。

这一差异有实际后果：方法可以被阅读、检查、替换和恢复；效果也依赖加载是否发生、模型是否正确遵循，以及工具条件是否满足。把技能文件移走或换成另一版，任务行为可能随之变化。

因此，“越来越熟练”应具体检查：是否保存了有效方法，后续任务是否真的调用，失败是否减少，新增成本是否合理。技能数量增加只是库存变化，不能直接证明能力提升。

## 9.6 谁能修改，怎样纠正旧方法

本版 Hermes 可以通过技能管理能力创建和修改方法材料，也支持多个技能来源及相应优先级。来源不同并不天然等于只读；实际文件权限、配置与管理路径共同决定能否修改。

这对共享技能尤其重要。若一个任务根据偶然失败修改了共享方法，其他任务可能继承它。因此修改应说明适用范围，保留可恢复的旧版本，并用新的输入验证，而不是只看原任务再次成功。

同名技能也可能来自不同位置。选择规则需要明确，否则用户以为在用自己刚改的版本，运行中却读到了另一个来源。排查时要确认实际命中的材料，而不只看名称。

## 9.7 维护不是不停自主重写

Hermes 的 Curator 对技能材料提供后台维护。这个版本区分按使用状态进行的确定性整理，与单独配置的模型辅助合并；候选来源、固定保留的材料和被任务引用的技能等，也有相应边界。

这是一项取舍：技能长期积累需要整理，但随意合并会丢掉适用条件、参考资源或任务依赖。归档可减少干扰，仍需要知道怎样找回；模型辅助整理可能提出更好结构，也会增加费用与误改风险。

维护结果应回到任务表现。若两个方法看起来相似，却依赖不同来源和权限，把它们合成一段更短文字未必更好。方法的支持文件与使用场景也属于需要保留的内容。

## 9.8 用一组新材料验证方法

把案例换成“原公告没有变化，但两篇转述都声称重大更新”。如果技能只写“多个来源都提到就收录”，它可能把同源转述当作独立证据。我们的草案则要求回到原材料，核对说法与范围。

再增加一个变化：“用户只要草稿，不要发送。”若技能内部默认投递，就必须服从本次范围并调整使用方式，不能因为方法曾经成功过就覆盖当前要求。

你现在完成了从单次任务到长期经验的第一段学习：任务卡定义目标，系统图连接职责，模型输入组织信息，工具取得结果，循环推进判断，上下文维持当前工作，历史保存过程，记忆精选长期事实，技能保存方法。后续将研究它们怎样在多入口、调度和协作中运行。

## 本章要点

- 技能保存带前提和验证方式的方法，不能把旧答案直接当作通用经验。
- 渐进披露将发现与详细加载分开，减少无关上下文，也依赖准确描述和选择。
- 加载、执行与验证分别观察；技能不能替代不可用的实际能力。
- 技能材料更新不同于模型权重训练，效果需在后续任务中检验。
- 来源、修改权限、版本和维护边界决定经验库能否可靠积累。

## 理解题

::: details 1. 为什么不把本周两条草稿直接存成“每周简报技能”？
草稿绑定当时的事件、来源和条件。可以保留其中的表达方式作为示例，但技能需要提炼材料范围、去重核实、未知处理和验收方法，才能用于下次不同输入。
:::

::: details 2. 技能已在库里，Agent 仍没有采用它，先检查什么？
先检查实际发现的来源、名称与描述是否相关，是否满足条件，以及详细内容是否真的进入了本次任务。再检查模型是否正确使用。文件存在、被发现和被加载不能混为一谈。
:::

::: details 3. 两份技能内容相似，合并后更短，是否就说明维护有效？
还要看前提、资源、权限、返回要求与任务引用是否保留。若删掉必要差异，较短方法可能误导后续任务。应保留恢复方式，并用能区分两种场景的新输入验证。
:::
