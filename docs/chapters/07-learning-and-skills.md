# 第七章：做过一次，下次为什么可能更熟练

第一次做简报时，你发现只读发布摘要会漏掉条件，于是补上“先确认稳定版本，再找相关源码和测试”。下次若能复用这套方法，就不必从零摸索。

Hermes 的技能系统提供了保存和按需加载任务方法的机制。这里的“学习”，要具体理解为**经验材料怎样被保存、调用与改进**，不能直接等同于模型权重训练。

<ChapterVerification chapter="07" />

## 7.1 事实与方法，适合放在不同地方

“读者偏好官方原文”是一条偏好，可以进入精选记忆；“怎样检查一个官方变更是否影响手册”是一套带前提、步骤和核实标准的方法，更适合技能（Skill）。

技能通常以 `SKILL.md` 为入口，还可以配脚本、参考资料和资源。说明应写清适用情境、必要输入、关键判断及预期结果，而不是把一次聊天的全部过程原样抄进去。

## 7.2 按需加载，减少无关方法挤占上下文

如果每次对话都读完整技能库，很快又遇到第五章的容量问题。Hermes 使用渐进披露的方式组织技能：先发现相关技能，再在需要时读取更完整的说明与资源。

这要求技能描述准确。一个叫“万能研究助手”的技能很难帮助选择；“核对官方稳定版本、判断已发布章节是否过期”则明确了用途。加载技能得到的是指导信息，真正的文件和网络操作仍由工具执行。

## 7.3 好经验需要前提，坏经验也可能被保存

下面两条都是**教学示意**：

| 保存下来的经验 | 风险或价值 |
| --- | --- |
| “接口失败时，多试几次总能解决。” | 忽略权限和永久错误，会重复浪费预算 |
| “先分清临时超时、参数错误与权限拒绝，再选择有限重试、改参或说明限制。” | 保存了判断依据，可迁移到新情境 |

一个技能能完成旧任务，不代表适合新版本。来源路径变化、工具接口调整和安全要求改变，都可能使旧方法失效。因此，技能也应有证据、适用条件和验证方式。

## 7.4 Curator 维护什么，不维护什么

Hermes 的 Curator 是面向技能材料的后台维护机制。该版本默认围绕 Agent 自建技能，跟踪使用情况并处理陈旧、归档等状态；其他来源技能是否能被管理，有明确范围限制。归档与永久删除也不能混为一谈。

尤其要注意：**自动状态维护与模型辅助合并是不同功能。** 本版文档把模型辅助整理作为单独配置，默认并非打开全部能力。不能把“存在维护器”写成“所有技能都在持续自主重写”。

## 7.5 本手册的维护技能也是一个例子

仓库中的“跟上官方最新”技能把版本检查、影响判断、图文修订和验证组织成可复用流程。脚本收集确定性资料，Codex 对照证据完成解释性工作。

这个技能被调用后仍然需要核实来源、审核改图和运行检查。写在技能里的“完成验证”，本身不构成已经验证的证据。

## 不写代码的小练习

用五行写一份“核对官方变化”的技能草案：适用场景、输入、关键判断、交付和验证。检查其中哪些是可复用的方法，哪些只是某次成功留下的偶然细节。

## 本章要点

- 技能保存任务方法，记忆保存精选事实与偏好，两者可以配合。
- 渐进加载减少无关方法进入上下文，但依赖准确的描述与发现。
- 可复用经验需要前提、适用条件和验证，失败习惯也可能被固化。
- 技能维护有范围与配置边界；改文档没有训练模型权重。

## 理解题

::: details 1. 将每次任务的最终答案保存为技能，问题在哪里？
最终答案可能只对当时的输入和版本成立。技能需要提炼方法、判断条件与核实方式；必要的具体资料可以作为参考，不应把偶然结果伪装成通用规则。
:::

::: details 2. 技能库越来越大，能否据此证明 Agent 越来越强？
不能。还要看技能是否相关、正确、易发现，是否减少失败或提高交付质量。重复和过期技能可能增加选择成本，需要通过新任务验证效果。
:::
