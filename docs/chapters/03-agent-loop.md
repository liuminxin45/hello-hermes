# 第三章：下一步做什么，什么时候停

查询发布记录失败了。一个 Agent 可以换来源，也可能原样重复同一个请求，直到耗光预算。两种表现都在“运行循环”，但只有前者利用了反馈。

本章看循环中的两个关键判断：下一步行动是否改变了信息状态，以及什么时候应该交付或说明限制。

<ChapterVerification chapter="03" />

## 3.1 一轮不等于一个用户问题

用户的一次要求，可能需要多轮模型请求。每轮准备当前信息，得到模型回复；回复可能包含最终文本，也可能提出工具调用。工具执行结果进入历史，再开始下一轮。

工具调用还可能成批出现，所以“迭代次数”“工具次数”“用户消息数”不是同一个计量。理解运行限制时，先看限制的究竟是哪一项。

## 3.2 用信息变化判断一次重试的价值

下面是**教学示意**：

| 反馈 | 有意义的调整 | 原样重试的问题 |
| --- | --- | --- |
| 临时超时 | 在允许范围内有限重试 | 无上限重试会拖垮任务 |
| 参数格式错误 | 修正参数后再执行 | 相同参数大概率仍失败 |
| 没有权限 | 说明边界或请求必要授权 | 重复尝试不能生成权限 |
| 来源没有覆盖该变化 | 换原始材料继续核查 | 换措辞搜索可能仍在重复二手说法 |

程序可以提供重试与恢复机制，模型也会根据错误调整行动。二者的责任不同：前者保证处理规则与限制，后者解释当前结果。好的错误反馈应帮助判断“为什么失败”，而不只是一句“工具出错”。

## 3.3 需要三类结束条件

第一类是目标完成：简报所需结论已有对应证据，输出符合范围与格式。第二类是运行边界：达到迭代、时间、费用或权限限制。第三类是外部结束：用户取消或系统中断。

它们不能统一写成“任务成功”。达到预算后生成一段说明，是这次运行的有效收尾，但缺失的资料仍然缺失。用户取消则不应被解释为模型已经自行判断完成。

<TeachingFigure src="/images/shared/stop.webp" alt="证据足够时交付，信息不足时查证，达到边界时说明限制" caption="图 3-2　教学示意：继续查证会产生下一次反馈；交付与说明限制都是退出，不回到循环。" />

## 3.4 Hermes 怎样承接这些责任

该版本的循环与各轮处理分布在 `conversation_loop.py` 和 `turn_*.py` 等模块中，配合预算、中断、工具执行和恢复逻辑。读源码时应跟着一次状态转换看，不把所有停止情况归结为一个简单的 `while` 条件。

预算限制可以防止无限运行，但限制本身不会证明质量。子任务还可能有自己的预算，所以评估一次完整任务时，应计入父任务及委托产生的开销。第十一章继续讨论这一点。

## 不写代码的小练习

为“临时超时”“参数错误”“权限拒绝”各写一条后续行动和停止条件。检查是否真的改变了导致失败的条件，以及退出时应该如何向读者说明未完成项。

## 本章要点

- 一次用户任务可能包含多轮模型请求和多个工具调用。
- 重试要对应失败原因，并受明确边界约束。
- 目标完成、达到限制与外部取消是不同结束原因。
- 运行次数和预算是控制手段，交付仍要有证据。

## 理解题

::: details 1. 页面持续返回“禁止访问”，增加迭代上限会解决问题吗？
不会直接解决。应先判断访问权限、地址和来源条件，必要时换允许的官方材料或说明无法核实。增加预算只会允许更多尝试，不会改变访问边界。
:::

::: details 2. Agent 在预算耗尽时写出“已完成”，你需要检查什么？
检查停止原因、实际取得的材料和原先交付标准。确认语不是完成证明；应明确哪些结论有证据、哪些未核实，以及是否真的产生了所需文件或输出。
:::
