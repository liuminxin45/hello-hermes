## 0. 给 Codex 的执行摘要：这一次到底要改什么

**不要再换主题、重写五章课程或增加一轮宏大的产品重构。保留现有“信息核验委托 → 新会话复用”的学习主线，把“文字驱动的三维展板”改成“动作驱动、旁边有人解释的工厂参观”。**

本轮必须交付的六个结果：

1. **场景让出来。** 桌面端采用独立右侧导览栏，不再用中央大面板覆盖主要设备；右侧栏内部上方放全局导览图，下方放导师短讲解。场景画布真实缩小并重新构图，不是简单把浮窗挪到右边。
2. **先看懂，再读懂。** 首屏只有具体任务、一个主按钮和一个能看出输入输出的小演示；默认讲解短句化，来源全文、实现边界、长答案按需展开。
3. **动作看得见。** 每个核心机制都有输入、处理、输出的完整动作。首次演示结束保留结果，并可进入明确标注的循环示意；绝不因循环动画再次执行业务、写记忆或增加工具调用。
4. **上下文变成可观察过程。** 资料逐批加入 → 接近整理线 → 保护当前首尾 → 整理员操作摘要设备 → 新摘要返回 → 容量下降 → 原始档案可回查，而不是直接从 70 跳到 35。
5. **局部突出、全局可知。** 非重点设备真正弱化，遮挡物进一步淡出；当前关注、实际任务状态和教学回放状态分别编码；右上角导览图同步显示节点与方向。
6. **以真实视觉证据验收。** 既运行现有测试，也提供关键视口截图、动画录屏、暂停/重播/恢复测试。构建通过不能替代“好不好看、看不看得懂”。

## 2. 根因判断：不是模型不够精美，而是观察机制不完整

现版已经有三维设备、信息连线、真实教学状态、上下文整理器和工人模型。缺少的不是“再放几个模型”，而是把动作组织成访客能看清的过程。[S3][S4]

目前的体验容易变成：

> 点击一个技术动作 → 短暂播放 → 工厂重新空闲 → 读一大段文字解释刚才发生了什么。

目标体验应该是：

> 看见一个具体困难 → 导师指向设备 → 设备完成可理解的动作 → 结果留在现场 → 用户决定继续、追问或重看。

**优先级顺序：构图与可见性 → 动作语义 → 时间节奏 → 信息层级 → 美术细化。** 不要先增加 Bloom、粒子数量和复杂模型。

## 3. 页面布局：让场景成为主角，导师站在旁边

### 3.1 桌面端推荐布局

```text
┌─────────────────────── 顶部：馆名 / 观察状态 / 暂停 / 更多 / 退出 ───────────────────────┐
│                                                                       │              │
│  03 / 05  工作台快满了                                                 │ 全局导览图   │
│                                                                       │ 约170px高    │
│                                                                       ├──────────────┤
│                  主要三维观察区域                                     │ 导师小赫     │
│             有明确前景、主设备、输入输出                               │ 1–2句短解释  │
│                                                                       │              │
│                不再覆盖中央长面板                                     │ 当前结果卡   │
│                                                                       │              │
│  跟上导师    全景                    动作示意·循环 / 暂停                │ 追问 / 证据  │
│                                                                       │ 主操作       │
└───────────────────────────────────────────────────────────────────────┴──────────────┘
```

- 右侧栏初始宽度 **320–380px**，大多数桌面尺寸用 360px。它是布局列，不覆盖场景。
- 全局导览图固定在侧栏顶部；讲解区在其下独立滚动；主操作固定在栏底。
- 问答、证据、详细原理在同一个侧栏内切换，不再叠一层大弹窗遮住工厂。
- 报告、考试、危险确认可继续使用真正的模态面板；日常讲解不使用模态。
- 场景顶部只保留短章节名。长问题、来源列表、计数明细进入侧栏，不堆在画布上。
- 侧栏收起后，画布扩展；顶角仍保留小地图/地图入口与“展开导师”。收起不暂停。

### 3.2 响应式规则

| 可用宽度 | 布局 | 要求 |
|---|---|---|
| ≥1100px | 左场景、右侧栏 | 主画布独立计算宽高；侧栏不盖设备 |
| 760–1099px | 左场景、紧凑侧栏，必要时收起深度内容 | 用容器宽度决定切换，不死守桌面宽度 |
| <760px | 上场景、下讲解区，使用真实上下分区 | 主场景目标不少于可用高度的55%；深入面板可临时展开并暂停教学 |
| 矮屏/横屏 | 保留最少控件，导师区域可滚动 | 不同时显示顶部长标题、大地图、大面板 |
| 无 WebGL / 减少动态 | 相同因果步骤的二维/文字替代 | 核心功能可完成；不生成虚假实景图 |

移动端的55%是起始目标，遇到浏览器工具条、键盘和大字号应重新布局，而不是裁切文字。320px宽、200%缩放也需可操作。

### 3.3 实施骨架

以下是布局骨架，不是对当前 DOM 可直接复制的最终补丁。Codex 应把现有 `#world`、`#mentor-panel` 与控制区迁入对应区域，并删除冲突的 `position:fixed / left:50% / transform` 规则。

```css
.study-shell {
  --rail-width: clamp(320px, 27vw, 380px);
  display: grid;
  grid-template-columns: minmax(0, 1fr) var(--rail-width);
  grid-template-rows: minmax(0, 1fr);
  position: fixed;
  inset: var(--header-height) 0 0;
  min-width: 0;
  min-height: 0;
}
.stage-region { position: relative; min-width: 0; min-height: 0; overflow: hidden; }
#world { position: absolute; inset: 0; }
.guide-rail {
  display: grid;
  grid-template-rows: auto minmax(0, 1fr) auto;
  min-width: 0; min-height: 0;
  border-left: 1px solid var(--line);
  background: var(--paper);
}
.guide-content { overflow: auto; min-height: 0; overscroll-behavior: contain; }
.guide-actions { padding: 12px 16px; }
.study-mentor {
  position: static; transform: none; width: auto;
  max-height: none; box-shadow: none; border: 0;
}
@media (max-width: 759px) {
  .study-shell {
    grid-template-columns: minmax(0, 1fr);
    grid-template-rows: minmax(0, 58fr) minmax(0, 42fr);
  }
  .guide-rail { border-left: 0; border-top: 1px solid var(--line); }

```

尺寸变更后，用现有 `ResizeObserver` 更新 `renderer.setSize()` 和 `camera.aspect`。Three.js 官方明确区分画布显示尺寸、绘制缓冲区与相机宽高比。[S11] 不能继续用全窗口尺寸去定位标签、射线拾取或构图。

### 3.4 构图验收

- 主设备及输入、输出口都位于真实场景视口内；右侧面板与设备屏幕投影不相交。
- 侧栏展开/收起、问答切换、窗口缩放后，相机不会突然回到工厂中心。
- 聚焦设备的屏幕包围框建议占场景宽度约30%–50%，按设备尺寸调整；不要仍以全工厂远景展示一个小零件。
- 不用扩大画布再用面板遮住的方式伪造“画布没变小”。

## 4. 首屏与导师文案：具体、短、先发生再解释

### 4.1 首屏替换文案

**标题：** 带着三条消息，走进 Agent 工厂。

**副标题：** 里面有重复，也有夸大。跟着小赫，看它查证后交出一份简报。

**主按钮：** 开始参观

**次入口：** 继续上次 / 直接看全景（仅在相应状态显示）

**短标识：** 教学模拟 · 不连接真实模型

首屏不再同时呈现完整样例简报、受众配置、学习目标、章节地图、设计时长及多段免责声明。完整边界放“本馆如何演示”里；涉及保存、发布、回放真实性的关键边界仍在对应动作前明确显示，不得藏起来。

首屏三维演示只做三件事：三张线索卡进入接待台 → 其中两张被标出同源 → 远处出现“两条草稿”的封面。不直接播完调查，也不把预览样例显示为用户任务已完成。

### 4.2 开始后的入场编排

| 相对阶段 | 场景 | 文字与操作 |
|---|---|---|
| 点击后立即 | 按钮反馈，侧栏出现，工厂门口接待台清晰可见 | “我来带路。先看看这三条消息。” |
| 接待 | 三张短线索卡依次摆上台，导师站在可见位置 | 一张卡只显示编号与短标题，不展示全文 |
| 问题出现 | 两张卡出现相同来源标记，第三张出现待核标记 | “它们说得不完全一样，得去找原文。” |
| 进入第一章 | 导师带路，镜头平滑到调度与工具交接处 | 主操作“去核对原文” |

整个入场目标是约12–18秒的可跳过演示，不是必须等待的加载或计时门槛。减少动态模式直接呈现关键帧和相同信息。

### 4.3 默认文字预算

- 场景章节名：尽量 **8–14个汉字**。
- 单次导师发言：**1–2句，约30–60字**，原则上不超过80字。
- 默认结果卡：**一个结果、至多两行**；详情可展开。
- 首层追问：最多两个推荐问题；深层问题放“更多”。
- 场景中的3D设备牌：**2–8字**；资料卡为短ID或短标题。
- 所有数值是编辑预算，不通过缩小字号、截断关键约束去硬凑。

### 4.4 五章短标题与现场台词

| 章节 | 场景短标题 | 代表性台词 | 画面必须同步发生 |
|---|---|---|---|
| 接到委托 | 先去找原文 | “模型提出了读取请求。真正去拿资料的是工具工人。” | 请求卡离开调度台，工人接单 |
| 查证与回路 | 查到的结果会改计划 | “这两篇说的是同一件事，只能算一条。另一篇把试用写成了全面开放。” | 同源卡合并，错误主张被改写 |
| 有限工作台 | 资料多了，怎么办？ | “档案都还在，但这次能摊在工作台上的资料有限。” | 档案与工作台并排可见，选取资料 |
| 交付与经验 | 交草稿，留经验 | “草稿交到了这里。偏好和方法要不要留给下次，由你决定。” | 草稿有来源；保存门等待选择 |
| 新会话复用 | 新会话带来了什么？ | 根据实际读取分支生成，见下方 | 空白工作台只加载实际存在的条目 |

第五章必须条件化：

- 偏好0、方法0、历史1：**“这次没有保存偏好或方法。我们只查回上次的记录；最新情况仍要重新核实。”**
- 偏好1、方法0、历史1：**“带回来了你的偏好和旧记录，但这次给研发同事看，以新要求为准。”**
- 方法1：**“这份核查方法可以继续用。不过它不是答案，还得读取最新公告。”**
- 禁用复用：**“这次不读取旧资料。工具和反馈循环仍然能工作，只是需要重新提供必要背景。”**

不要为了展示“记忆有效”偷偷预置已保存条目；不要把所有分支都写成“已读取偏好和方法”。

### 4.5 文案去重与渐进展开

`render()` 当前把太多数据追加到同一导师区。[S5] 改为一个视图模型：

```js
// 建议结构，不是现有接口。
{
  cue: '两条报道指向同一份公告。',
  result: { title: '已合并重复消息', detail: 'S1 + S2 → 同一事件' },
  primaryAction: { label: '继续核对另一条', intent: 'advanceChapterBeat' },
  suggestedQuestions: ['为什么不能算两条？', '谁决定继续查？'],
  evidenceRefs: ['S1', 'S2', 'A1'] // 点击“看原文”后才展开全文

```

不要同时显示 `chapter.lines + event.detail + corrections全文 + 实际输入全文`。不要从所有句子机械截取前60字；要为各节拍编写真正不同的短讲解。

## 5. 动画核心规则：业务只执行一次，解释过程可以反复看

### 5.1 分清三类“动”

| 类别 | 表达什么 | 是否可以循环 | 对任务数据的影响 |
|---|---|---|---|
| 任务事件呈现 | 解释已经记录的请求、工具回执、保存等事件 | 首次播放一次 | 事件由 engine 产生；播放器本身不执行业务 |
| 教学动作示意 | 重看某次事件的动作原理 | 可以默认循环，必须有“循环示意”标识 | 不新增任务事件、不重写档案、不增加实际计数 |
| 环境待机 | 小灯、轻微机构待机 | 可以极低幅循环 | 无业务语义，不能冒充正在处理任务 |

**禁止“为了让工厂一直动，把 `retrieveSources()` / `saveExperience()` 放进动画循环”。** 也禁止让已经完成的业务一直显示“执行中”。

建议把“本次事件已完成”和“正在播放该事件的动作示意”同时呈现：

> 本次读取：已完成　｜　画面：循环示意

保留真实性，但不需要每三秒弹一次长免责声明。

### 5.2 每个关键动作采用统一六拍

1. **到位：** 镜头到达，聚焦完成，人物与目标设备都可见。
2. **准备：** 资料或请求靠近输入口，机构回应。
3. **处理：** 工人/设备执行有意义的动作，不能只转一个圆环。
4. **交接：** 有身份的数据卡沿真实关系方向移动。
5. **结果：** 结果落到目标位置，并保持可见。
6. **停留/重看：** 等待用户继续；可自动播放无副作用的短循环示意。

主线常规机制首次演示建议6–9秒；复杂上下文演示建议22–30秒。交付结果至少保留到用户继续，不要1.1秒后完全消失。用户始终可以跳过或加速，不强迫看满时长。

### 5.3 循环应反复“解释动作”，不是不断“生产新结果”

例：工具读取示意每轮按“接收请求 → 查看来源 → 返回回执”执行。

- 请求卡与回执始终绑定同一 `sourceEventId`。
- 下一轮开头用淡出/回到示意初态，不能显示反向数据流在业务中真实发生。
- 草稿数、历史条目、读取次数、用户保存选择不随循环增长。
- 角色可以重复示意拿取动作，但场景注明这不是再次访问外部服务。
- “暂停”冻结当前示意时间；“重看”从该示意开头；“继续”结束示意并进入下一个教学节拍。

建议默认只循环当前主设备及一条相关关系，不让全厂同时持续播动画。

### 5.4 修复当前暂停与观察语义

将现有 `held = paused || collapsed || panel.open || ...` 重构为显式原因集合。[S5]

```js
// 设计骨架：保留真正的暂停原因，不把面板折叠当暂停。
const pauseReasons = new Set();
// 可用值：user、question、report、exam、hidden、contextLost。
function setPauseReason(reason, enabled) {
  if (enabled) pauseReasons.add(reason);
  else pauseReasons.delete(reason);
}
function presentationPaused() { return pauseReasons.size > 0; }
```

- 收起导师：只重排布局，动画继续。
- 打开追问：暂停自动主线和教学时间，不销毁当前节拍。
- 关闭追问：只移除 `question`，不能把用户原本的 `user` 暂停清掉。
- 手动环顾：相机不再被抢回；一般不必停止局部动作，提供独立暂停。
- 页面隐藏：停教学时钟、降低/停止渲染；返回不跳过中间动作。[S12]
- 暂停界面只控制本馆教学，不声称能暂停真实外部工具。

### 5.5 主操作不要一直是“跳过动画”

当前 `render()` 在观察期间隐藏继续按钮，并把跳过作为主按钮。[S5] 这让用户最醒目的可用操作变成“绕开动画”。

改成：

- 播放时：主操作“看下一步”可用；旁边小按钮“暂停”；“重看”在可重播后出现。
- 进入重要决定：主操作是具体决定，例如“去核对原文”“保存所选资料”。
- 结果停留时：主操作“继续”；次操作“再看一次”；追问一直可达。
- 不需要用户分别点击“生成请求”“派发请求”“让工具读取”“接受回执”才能走完同一个概念。中间技术步骤由教学编排串起，保留必要的授权与业务校验。

## 6. 上下文容器：完整分镜与数据模型

### 6.1 先说明真实边界

这仍然是**同一委托的长过程教学回放**，不是声称当前三条短材料已用满真实模型上下文。100格、70格整理线和20格预留是教学参数，不是 Hermes 官方固定默认值。Hermes 的实际压缩与尾部保留受版本、模型和配置影响。[S6][S14]

保留 `rules/head/middle/tail` 的教学分区，但主界面优先显示“常驻规则 / 起始要求 / 中间过程 / 最近交接”；点开后才显示英文术语。

### 6.2 保留现有压缩机，补上角色与物料交接

当前已有 `compressor`、`piston`、`summary`，无需再另造一套模型。[S3] 改造为：

- **资料入口：** 传入的是消息/查询结果卡，不是实体原料。
- **容量容器：** 用统一尺度的5格资料包表示占用；侧边有70格整理线和80–100格预留带。
- **整理员：** 一个负责演示摘要工作的角色，走到机台、选择中段、阅读/整理、交回摘要。
- **摘要机：** 更像把多份资料整理成新卡片的装置，而不是只靠液压把文本无损压扁。
- **档案柜：** 原始资料始终留存；存在明确的来源编号。

解释边界：整理员是压缩流程的具象角色，不意味着 Hermes 必然有一名独立子 Agent。摘要可能由辅助模型产生，具体绑定依固定实现核实，不在主线编造隐藏思考。

### 6.3 建议时间轴（可跳过、可暂停）

| 时间参考 | 演示阶段 | 可见动作 | 资料占用与台词 |
|---|---|---|---|
| 0–2秒 | 基础工作台 | 规则、起始要求、最近一组交接已在台上 | 25/100；“这是当前的一次工作输入。” |
| 2–4秒 | 第一次加入 | 10格查询结果卡进入，中段增加 | 25→35；“又查回了一份资料。” |
| 4–6秒 | 第二次加入 | 新卡进入，原最近交接移入中段，尾部更新 | 35→45；“上一轮结果也要留着继续判断。” |
| 6–8秒 | 第三次加入 | 比较记录进入 | 45→55；容量上升，侧边计数同步 |
| 8–10秒 | 第四次加入 | 一组工具结果进入 | 55→65；整理线开始被强调 |
| 10–12秒 | 到达整理线 | 5格资料进入，信号变为待整理 | 65→70；“还没装满，但后续处理需要余量。” |
| 12–15秒 | 保护与选取 | 本次首尾边框锁定，中段45格被选中 | 规则5 + Head10 + Middle45 + Tail10 =70 |
| 15–20秒 | 摘要处理 | 整理员读中段卡，机台生成10格新摘要卡 | 台上出现“条件、来源、待办”三项短标记 |
| 20–23秒 | 返回工作台 | 10格摘要返回中段，空位明确增加 | 5+10+10+10 =35；“下一轮会读这份摘要。” |
| 23–26秒 | 回看结果 | 70→35前后卡并排，档案柜原卡不变 | “原文仍在档案里；摘要可能漏细节。” |
| 之后 | 保持/循环示意 | 当前结果保持，支持重播完整过程 | 循环只改呈现，不改委托和原始证据 |

以上计数保持现有70→35的教学例子，不为了视觉重做真值。[S6] 中间每包几格和动画时长可调，但计数、块数、容量标记与前后结果必须一致。

### 6.4 Head/Tail 的关键真实性约束

**新增资料期间，Tail 会滚动；进入某一次压缩操作后，才保护该次选定的首尾集合。** 不要把绿色尾部做成从入场到结束永远不变的一块。

建议每张资料卡有稳定ID。增长阶段把上一轮尾部交接移到中段，新交接成为尾部；触线后冻结本次选择。保留工具请求/结果的配对，不把半个交接移走。上述是教学模型的规则，不宣称所有压缩实现都原样保留全部尾部内容。[S14]

### 6.5 摘要必须展示“重写”，不能只有“缩小”

主画面从三张短片段：

- “Atlas：仍需申请审核”
- “Delta：PDF / Markdown”
- “仅草稿，不发布”

整理出一张更短、仍带条件和来源的摘要卡。真正完整文案放侧栏。

坏摘要对照复用现有教学分支：把“需要申请审核”丢失后，明确显示**来源没变、工作摘要变了、下一步可能误判**。允许查看档案修正，但不暗示正确摘要一定无损。

### 6.6 结构化采样，而不是写死末态

## 7. 把具象手法扩展到所有部件

不需要增加高精度资产。**不同部件应该有不同的“手势和结果”，而不只是不同牌子。**

| 部件 | 现有可复用资产 | 应看到的动作 | 短标签 | 不能造成的误解 |
|---|---|---|---|---|
| 委托入口 | 柜台、资料卡、导师 | 三张线索入场，形成带ID的任务夹，原文登记 | 接收委托 | 接收不等于理解正确或完成 |
| Agent Loop | 中央台、圆环 | 接收请求→派发→收到反馈→下一张动作卡改变 | 调度 | 循环不是无脑反复，也不是每次固定走所有机器 |
| 模型判断 | 显示器、判断台 | 输入卡进入，只显示可观察的回答/工具请求分叉 | 判断下一步 | 不表演未经来源确认的模型内部思维链 |
| 工具与注册表 | 工具柜、工人 | 目录抽屉指明可用工具；工人接单、取来源、交回回执 | 工具执行 | 工具工人不默认等于另一个独立Agent |
| 历史与FTS | 资料柜、圆柱、索引屏 | 记录写入；关键词命中索引，再取回原文编号 | 历史检索 | 索引不是原文；关键词检索不冒充向量语义检索 |
| 偏好记忆 | 左侧小抽屉 | 用户允许保存后卡片进入；新会话实际读取时才出来 | 偏好 | 不把一次选择自动当作永久偏好 |
| Skills | 右侧书架、方法册 | 打开方法册，步骤卡放在工作台旁；可修订版本 | 方法册 | 阅读方法不是自动执行，也不是权重更新 |
| 上下文 | 容器、压缩机、整理员 | 持续入卡、触线、摘要替换、释放空间 | 工作台 | 工作上下文不是所有持久数据 |
| 交付 | 成品台、纸张 | 两份草稿逐页展开，来源标记与未确认项可见 | 草稿交付 | 不得自动发送；工具成功不保证目标完成 |
| 轨迹/复盘 | 记录台、关闭的训练设备 | 记录本次可观察事件；训练设备默认保持关闭 | 过程记录 | 记录不等于RL训练 |

### 工人和导师的最低动作标准

- 角色有明确站位、朝向和手部动作，不只瞬间出现在机台边。
- 简单分组骨架足够：身体、头、两臂、两腿各有枢轴。走路腿部交替、接单抬手、处理前转向目标。
- 提供脚下接触阴影或清晰接地关系，避免像贴图浮在空中。
- 导师和工人颜色/服装不同，但意义也用形状、短名表达，不能只靠颜色。
- 导师讲解不会改变任务真值；工人动作只是工具执行的教学表现。
- 修复 `toolRequest/toolResult/toolError/skill` 的人物与灯光映射，加入逐项测试。[S3][S4]

## 8. 视觉聚焦：这次需要真正的半透明，而不仅是变灰

### 8.1 双维度状态不变，效果强度重标定

沿用“关注度与运行状态独立”的原则。当前实现已经有这两个维度，不要删除；问题是效果太弱、背景太完整。[S3][S4]

| 对象 | 外观起始值 | 标签 | 动作 |
|---|---|---|---|
| 当前讲解部件 | 保持原始不透明度；柔和轮廓 | 完整短标签 | 按实际教学片段，不因聚焦伪造运行 |
| 当前输入/输出的关联部件 | 约0.50–0.65倍原始不透明度 | 只显示至多2个必要短标签 | 参与当前交接时才明显运动 |
| 其他背景部件 | 约0.12–0.22倍原始不透明度；降低饱和度 | 隐藏长牌与默认状态名 | 停显著动作，保留低幅待机或完全静止 |
| 挡住焦点的背景 | 在所属等级上再减弱，必要时隐藏非必要内件 | 不显示 | 不参与当前动作 |
| 地台、路径、必要框架 | 保留足够轮廓以维持空间方向 | 无说明文 | 基本静止 |

主焦点清晰，背景要明显“退后”。不要再把0.48的关注权重仅映射成轻微颜色变化，然后声称实现了半透明。

### 8.2 透明只是手段：一起处理内部结构和阴影

全厂多层玻璃式透明会暴露大量内部边线，并有透明排序限制。[S9] 因此：

- 背景设备优先显示简化外壳/轮廓，隐藏抽屉内部细节、监视器文字和重复面片。
- 焦点设备恢复完整零件；关联设备保留输入/输出口，没必要展示所有螺丝。
- 背景人物、标签、关系箭头、阴影也应降权。只淡化机身、留下深色阴影与高亮字牌，会继续抢注意力。
- 遮挡判断需要考虑目标的可读面积，不能只依赖穿过中心的一根射线。
- 允许用户一键“看全部设备”，但默认返回导览后恢复焦点规则。

### 8.3 材质实施注意事项

当前 `staticRecords` 已克隆设备材质，这个基础可以复用。[S3]

- 保存每个材质的初始颜色、不透明度、透明标记、深度写入、阴影设置；恢复时按初值恢复，不能统一设成不透明。
- 玻璃仍然是玻璃：主设备的原玻璃透明度0.17不应强行改成1。
- 同时支持单材质和材质数组；避免每帧克隆材质或创建纹理。
- 真正发生透明状态切换时才更新相关标记；不要每帧无条件 `needsUpdate=true`。
- 背景透明通常不写深度，但仍需正确深度测试与排序。`renderOrder` 不是消除遮挡的万能开关，不能把焦点强行画在所有物体前方。[S10]
- 对大部件可使用简化幽灵代理网格，而不是把复杂内部层层透明；先实现基础版，出现排序问题再升级，不直接引入昂贵的全局后处理。

```js
// 关注/遮挡合成示意；初值来源于当前物体自己的原材质。
function targetOpacity(record, tier, occluded) {
  const tierFactor = { focus: 1, related: 0.60, background: 0.18 }[tier];
  const occlusionFactor = occluded && tier !== 'focus' ? 0.35 : 1;
  return record.baseOpacity * tierFactor * occlusionFactor;
}

function approach(current, target, dt, rate = 10) {
  return current + (target - current) * (1 - Math.exp(-rate * dt));
}
```

过渡起始目标为300–600ms；先完成主要聚焦，再播放动作。不要再次让2.5秒淡化过程长于主体动作本身。

### 8.4 高亮不等于全身发光

- 当前关注：薄轮廓/平台边界 + 清楚标签。
- 当前处理：输入口、核心机构、输出口按顺序局部点亮。
- 等待用户：静态待办图标或低幅呼吸灯，不继续执行动作。
- 已完成：留下完成标记和结果物，停止“运行中”语义。
- 回放：播放标记或虚线边框，短字“示意”；不能与实际执行状态使用完全相同表示。
- 错误：明确停在失败位置，标注原因与可恢复动作；不只闪红灯。

浅色背景下优先增加局部结构对比，而不是盲目提升发光强度。避免整个页面因为“强调焦点”变成一团白光。

## 9. 右上角全局导览图：不是装饰，而是持续回答“我在哪里”

### 9.1 推荐形式

首版采用 **SVG 简化拓扑图**，占侧栏顶部约320×170px。不是第二个持续渲染的 Three.js 场景，不是把复杂工厂截图缩小。

保持稳定方位和节点位置，不随主相机旋转。主画面负责空间体验，导览图负责系统关系。

建议布局：

```text
           [入口]
              ↓
 [历史] ⇄ [调度] ⇄ [模型]
              ⇅        ↑
 [偏好/方法] ↔       [工作台]
              ⇅
           [工具]
              ↓
           [交付] ··· [记录]
```

这是概念布局示例。实际连接必须从 `FLOWS` 导出，不凭这张示意图新增错误的数据通道。工作台、历史、记忆是支撑多个轮次的机制，不是每次必须按顺序经过的流水线。[S4]

### 9.2 视觉语法

| 标识 | 含义 |
|---|---|
| 外圈选中框 | 导师正在讲哪一个部件 |
| 实心短脉冲或处理中图标 | 当前呈现的处理节点 |
| 带箭头的移动短划 | 当前片段的数据方向 |
| 小勾与静态结果点 | 本次事件已完成，仍可回看 |
| 虚线播放框 + “示意” | 正在重播教学动作，不是新任务 |
| 问号/等待符 | 等待用户决定或新的输入 |

不能只靠颜色。平时最多强调2–3条关系，其余为低对比细线；轨迹旁路默认折叠为一个记录标记，避免蜘蛛网。

### 9.3 交互规则

- 点击节点：进入只读观察，不调用 `act()` 或生成新任务事件。
- 当前未讲到的节点可看短介绍；不把自由观察自动记为章节完成。
- 点击“跟上导师”回到主线当前节拍，不重置任务。
- 鼠标悬停/键盘聚焦显示一句职责；支持Tab和Enter操作，不能只监听SVG坐标。
- 主画面、侧栏标题、小地图焦点必须同源，不能各自维护不同 `selectedNode`。
- 暂停后地图粒子同时停止；完成后保持状态；回放时明确显示示意状态。
- 窄屏收为“当前位置：工具”小条，点开导览图；不能挤掉主设备。

### 9.4 数据接口建议

```js
// 从统一 presenter 快照生成，地图不能调用业务执行函数。
{
  focusNodeId: 'context',
  presentationMode: 'teaching-replay',
  phaseId: 'summarize',
  activeNodeIds: ['context'],
  activeFlowIds: [],
  sourceEventIds: ['...'],
  resultStatus: 'recorded',
  paused: false
}
```

复用 `NODES / FLOWS` 及新的语义动画映射。不要维护一份全新的小地图边表，否则下次修改主场景关系后会再次不一致。

## 10. 镜头、导师和场景可读性

### 10.1 默认镜头不持续旋转

自动带路用于**转场**，不是阅读期间的持续环绕。当前用户需要理解动作，镜头应在机台动作阶段基本稳定。

建议每个重点部件配置三个可选机位：

- `establishing`：看见部件、导师和两个相关区域；用于到站。
- `action`：看清输入、核心动作、输出；用于主要教学。
- `detail`：查看某个零件，如摘要出口、索引抽屉；用于追问。

不要求用户手动走路才能看清。保留自由观察，但“跟上导师”直接放在场景控件或侧栏，不再藏在“更多→设置”里。

### 10.2 人物移动与相机移动都应有连续性

目前 `focus()` 直接把导师移动到下一部件旁，工人也按操作类型直接设位置。[S3] 这是缺少参观连续感的可确认原因之一。

建议：

1. 导师先转身、指向目的地。
2. 沿简短可见路径行走，镜头平稳跟进。
3. 到站后导师让开核心设备，站在侧前方。
4. 讲解时朝向设备或访客，不遮住输入/输出口。

只实现简单路线插值与肢体摆动即可，不必引入完整寻路系统。减少动态模式切到目的地关键帧，不强行慢慢飞行。

### 10.3 正确构图，防止“透明了还看不清”

- 相机计算采用真实 `.stage-region` 可用矩形，不是 `window.innerWidth`。
- 将主设备及输入输出的 `Box3` 作为构图范围；不要只对准机台中心点。
- 避开上方章节条、短标签与底部控件的安全区；DOM面板变更后重新评估。
- 主设备高于其它平台时，应有能看到内部的角度；不能让容器前壁/牌子挡住内容。
- 主图不跟随小地图旋转，保持认知方向稳定。
- 手动相机状态下不自动抢回。需要跨章继续时，用明确按钮回到导师位置。

### 10.4 修复问答中的相机返回栈

现有逐题 `inspectPart()` 压栈、退出仅恢复一次的逻辑，需要验证并修正。[S3][S5]

改成：打开问答时保存一个 `originView`；问第2、第3个问题只替换目标，不继续压入原位。关闭问答恢复该 `originView` 一次，然后清理引用。用户在问答中手动旋转时，提供“保留当前视角”与返回主线的明确规则，不靠隐式多层栈碰运气。

## 11. 清理空中长文与标签：把空间留给动作

### 11.1 删除/迁移的具体内容

把 `scene.mjs::sign()` 中这些解释性句子迁移到侧栏或追问：

- “当前输入 · 不等于全部档案”
- “原始证据 · 历史与笔记”
- “偏好 ≠ 方法 ≠ 权重”
- “有来源的简报 · 不自动通知”
- “可观察轨迹 · 不自动训练”
- “请求 → 结果 → 下一步”等重复整句牌子

它们讲的原理可以保留，但不适合一直悬在三维空间中。[S3]

替换为短设备牌：“工作台”“历史”“偏好”“方法”“草稿”“轨迹”。每台设备只保留一种主要命名方式；默认不同时出现一个3D句子牌和一个DOM句子标签。

### 11.2 长内容移入稳定二维区域

资料卡在三维中只显示 `S1 / A1 / 旧记录 / 摘要` 等身份。点击后侧栏显示原文、来源与用途。原文不直接贴在远处三维平面上让用户旋转辨认。

`Head / Middle / Tail` 可作为近看时的辅助标签；远看只显示“起始 / 过程 / 最近”。

### 11.3 标签系统规则

- 导览时最多显示主焦点及至多2个关联标签；其余通过小地图维持定位。
- 标签带短引线或明确锚点，不能漂在离设备很远的空中。
- 对标签进行屏幕矩形碰撞检测；重叠时优先保留焦点，其次当前动作节点。
- 视锥外或相机后方隐藏；不要只做单一 `p.z>1` 判断后默认全部正确。
- 不要给所有空闲设备反复写“空闲”；仅在用户查看状态时显示。默认状态文字用于当前运行、等待或错误。
- 对章末已经完成的节点显示“已完成/可回看”，不是全都回到无意义的“空闲”。

## 12. 让人物、动作、字幕、地图共用一个呈现时间轴

### 12.1 不再增加并行的状态来源

现有 `task / tour / learning` 分离应保留。[S1][S6] 新的动画不需要第四套业务引擎；只需要一个可采样、可暂停、可回放的**呈现层**。

```text
engine：处理用户授权的业务意图，只产生一次任务事实
    ↓ 已发生的事件 / 教学分支描述
presenter：将事实排成观察片段，控制节拍、暂停、循环和字幕
    ├── scene：设备、人物、资料运动
    ├── guide rail：短讲解、结果卡、下一步
    ├── minimap：节点、方向、播放模式
    └── learning：哪些片段被观察/略过，报告可引用哪些证据
```

不要让地图点击、相机切换、角色动画完成回调去直接调用任务函数。

### 12.2 建议呈现状态

```js
// 新字段建议，不是当前代码现有接口。
{
  clipId: 'read-source',
  sourceEventIds: ['event-id'],
  mode: 'event-presentation', // event-presentation | teaching-replay | ambient
  status: 'playing',         // playing | paused | holding | finished
  phaseId: 'handoff',
  elapsed: 3.2,
  speed: 1,
  repeat: false,
  cycle: 0,
  focusNodeId: 'tools',
  pauseReasons: [],
  originView: null,
  resultAcknowledged: false
}
```

`cycle` 是视觉循环计数，不得出现在“真实工具调用次数”或学习成绩里。

### 12.3 数据驱动的分镜，不把动画写进 `render()` 大分支

建议在当前 `scene-state.mjs` 上扩展时间轴，新增一个小型 `storyboard.mjs` 保存静态片段配置；`minimap.mjs` 管地图。必要时将 `scene.mjs` 中聚焦/标签计算提取成 `focus-visuals.mjs`。**优先控制在2–3个新增模块，不建立通用游戏引擎或复杂插件层。**

```js
// 示例：仅表达结构，Codex应接到现有director而不是复制第二套director。
const readSourceClip = {
  id: 'read-source',
  duration: 8,
  focus: 'tools',
  phases: [
    { id: 'receive', start: 0, end: 1.5, cue: '请求交给了工具工人。' },
    { id: 'lookup',  start: 1.5, end: 4.5, cue: '它去读取原始公告。' },
    { id: 'return',  start: 4.5, end: 6.5, cue: '结果沿这条线返回。' },
    { id: 'result',  start: 6.5, end: 8, cue: '拿到原文，还需要核对说法。' }
  ],
  resultHold: 'until-continue',
  repeatAs: 'teaching-replay'
};
```

所有位置尽量从绝对片段时间计算，而不是持续累加 `position.x += ...`。这样拖时间、暂停、重播和恢复才可得到一致画面。

### 12.4 明确业务完成与画面完成的边界

当前 `act()` 会先修改教学任务并拿到事件，再让场景播放。[S5] 可以继续采用事件回放式呈现，但要注意：

- 引擎事实已产生，不意味着UI要马上把所有未来结果展开，让用户在动画前读完答案。
- 用 `revealedEventIds` 或当前片段的可见边界控制UI，不篡改原始任务事实。
- 后续事件可以已排队，但地图、状态灯、结果卡必须显示当前观察位置，不泄露整个队列的末态。
- 跳过动画可展示同一结果；学习记录标“已略过动画/已查看结果”，不得伪称看完全过程。
- 回放结束不得调用 `retrieveSources`、`saveExperience`、`deliverDraft` 等业务函数。
- 本地教学没有远程副作用，但实现结构仍应保持这个边界，防止未来接真实工具时沿用错误机制。

### 12.5 统一时间与渲染循环

当前 `scene.mjs` 与 `app.mjs` 各有帧循环，后者依据前者 `busy()` 自动完成观察。[S3][S5] 不必为了优化立刻彻底重写，但必须避免两个时钟各自推进教学逻辑。

建议一个呈现时钟，场景采样该时钟；应用只订阅语义阶段变化。暂停不推进，隐藏页恢复不补跑错过的几十秒。`requestAnimationFrame` 在多数浏览器后台页会暂停，不应依赖后台正常回调来完成过程。[S12]

```js
// 示例逻辑：t只属于视觉回放，不能作为业务状态依据。
function tick(now) {
  const dt = Math.min(Math.max((now - lastFrame) / 1000, 0), 0.05);
  lastFrame = now;
  if (!presentationPaused()) presenterTime += dt * playbackSpeed;
  const frame = sampleStoryboard(presenterTime, clip, sourceSnapshot);
  renderScene(frame);
  updateMinimapIfChanged(frame);
  updateGuideOnSemanticChange(frame);
  requestAnimationFrame(tick);
}
```

页面重新可见时重置 `lastFrame`；不要用一次巨大的时间差跨过所有中间阶段。长帧时间处理要以“不漏掉学习因果”为优先，计时效率不等于真实业务性能。

### 12.6 事件名称与资产映射必须可校验

建立一个明确表，覆盖实际存在的操作：

| 操作 | 角色动作 | 指示灯 | 关系 |
|---|---|---|---|
| `toolRequest` | 接单 | 工具入口 | `tool-call` |
| `toolResult` | 带回资料 | 工具出口/调度接收 | `tool-result` |
| `toolError` | 停止、交错误回执 | 工具错误 | `tool-error` |
| `memory` | 取偏好卡 | `preferenceLamp` | `memory-read` |
| `skill` | 翻方法册 | `skillLamp` | `skill-read` |
| `history` | 查索引、取档案 | 索引后原文 | `history-query/history-result` |
| `compress` | 整理中段、交摘要 | 工作台/摘要机 | 当前压缩分镜 |

发现新事件没有配置时，提供安全的静态结果呈现，不悄悄用错误设备替代。代码校验应能发现未覆盖项、无效节点和不存在的flow。

## 13. 其他需要一起解决的问题

### 13.1 不要把用户当成流程调度器

目前每个小步骤都有技术化按钮，容易让用户不断点“生成、读取、修正、下一章”。这保留了可观察状态，却牺牲自然感。[S5]

保留一个明确目标操作，内部由编排自动呈现若干步骤；在真正需要用户决定时才停下来：是否开始核验、是否保存偏好/方法、是否重看/追问。不要去掉保存同意，也不要让主线自动模拟用户作出同意。

### 13.2 简化准确性提示的默认表达

当前首页和面板包含多项很负责任的说明，例如设计时长未验证、问答非实时模型、没有冻结远程工具。[S1][S5] 这些应保留，但不应每次都盖在主体验上。

- 常驻一个“教学模拟”标识。
- 保存前明确告知本机存储与选择内容。
- 回放时明确“动作示意/回放”。
- 详细来源、固定版本、测试范围放“原理与依据”。
- 不把“减少默认文字”误解为删除边界；也不把“真实准确”理解为每个屏幕都写一页免责声明。

### 13.3 维护一个“我当前知道什么”的简短结果

每章右侧固定一句结论，不要求用户回忆已经闪过的动画。例如：

- “请求不是执行。”
- “反馈改变下一步。”
- “保存过，不等于本轮都看见。”
- “偏好和方法不是模型权重。”
- “复用旧资料，仍要核查新事实。”

不要把五句同时贴在工厂上。当前只显示当前一句，章末/报告再汇总。

### 13.4 声音是可选增强，不是遮挡补丁

可以增加轻微接单、完成、整理提示音，但默认不自动有声。语音导师放后续，不以TTS替代文案精简或清晰动作。任何声音都不能是唯一的状态提示。

### 13.5 退出、刷新与旧记录

动画中刷新后应恢复任务事实和可重新观看的片段，不把视觉循环计入业务。用户离场不必填昵称、不必考试、不必下载。只为视觉优化不要无意义提高业务schema版本；若确需增加持久字段，提供显式兼容默认值与迁移测试。[S1][S6]

## 14. 性能、可访问性与截图

### 14.1 性能约束

- 保留低多边形风格和当前固定Three.js版本，不以资源包膨胀换细节。
- 用几何复用/实例化处理资料包；一组包不能每帧创建和销毁。
- Canvas文字纹理仅在文本改变时更新，替换后释放旧纹理。
- 材质与几何在初始化或换场时创建；动画只更新变换、数值和必要可见性。
- DOM字幕和计数按语义变化更新，不每帧重建整个导师HTML。
- 地图用同一时钟，必要时限制刷新频率；没有必要再建第二个WebGL上下文。
- 页面隐藏暂停；减少动态模式停止非必要循环；设备质量档可调像素比、阴影、抗锯齿。
- 目标可先设普通桌面稳定接近60fps、低配可用档稳定接近30fps，但必须注明测试机器、分辨率和质量档；未测不得写“稳定60fps”。

### 14.2 暂停与减少动态

循环示意必须有持久的暂停控制。自动移动/更新且与其它内容同时存在的动画，需要按适用条件提供暂停、停止或隐藏；W3C的相关说明不能被简化为“只要有动画就全部禁用”。[S13]

减少动态模式不是跳过知识：使用“接收 / 处理 / 返回 / 结果”关键帧，允许逐步查看。左右移动、空间旋转、大幅闪烁不是学习所必需。

主要控件建议保持至少44×44 CSS像素的触控区域，这是本项目易用性目标，不在报告中冒充所有WCAG条款的统一最低值。状态同时使用文字、图标和颜色。日常侧栏不错误地抢走键盘焦点。

### 14.3 截图与报告保持真实

现有 `capture()`、照片slot和失败记录机制应保留，但将触发点改为分镜语义标记，例如：

- `tool-result-visible`：请求、工具与返回结果同时可辨。
- `compression-replaced`：首尾保护、中间摘要、70→35、原档案同时可辨。
- `reuse-loaded`：只显示实际被加载的偏好/技能/历史。

不要依赖“操作时间超过45%”作为所有设备的通用最佳截图时刻。[S3]

截图是实际渲染场景，不包含遮挡主体的大面板。需要16:9时，单独用确定的捕获相机/渲染目标生成，避免将侧栏缩窄后的非16:9画布拉伸；拍摄后恢复主相机/渲染状态。报告元数据记录真实输出尺寸、片段ID、事件ID、是否回放。未拍到就记录缺失，不补造宣传图。

### 14.4 新增交互不能破坏信息可达性

原理来源、工具边界、用户选择仍必须可找到。精简的是默认呈现，不是删除深度。文字模式应该使用同一分镜数据，避免三维讲一套、文字又是一套。

## 20. 一句话验收目标

**用户不必追着字幕理解一瞬间已经结束的动作，而是能从工厂里看见问题发生、看见部件如何处理、看见结果留在哪里；想深入时再问，想看全局时抬眼就知道当前位置。**

如果最后只是“对话框换了位置、设备多闪了几下”，本轮没有完成。真正的完成，是同一份可信任务状态通过场景、人物、地图和短讲解，被连贯地讲清楚。
